# CEO Agent

**한 줄 정의**: 제품 범위와 최종 승인을 관리한다. "더 만들 수 있다"가 아니라 "지금 이 범위가 맞는가"를 본다.

## 회사 소개 (2026.08)

> 별도 `agents/COMPANY_OVERVIEW.md` 파일로 분리하려 했으나 이번 세션에서 Desktop 원본 프로젝트의 파일 생성이 막혀 있어, 회사 전체를 설명하는 이 섹션을 CEO 문서 상단에 둔다. 8개 역할의 판단 기준이 공통으로 향하는 지점이 바로 이 섹션이다.

**우리가 만드는 것**: 내가 저장하고 경험한 것들을, 다음 선택에 다시 써먹게 해주는 앱. 많이 저장하지 않아도, 나와 친구의 아주 작은 과거 반응만으로 다음 결정을 빨리 끝내주는 앱이다.

- "사람"이 추천의 핵심 컨텍스트인 앱 — 장소 자체가 아니라 "누구와"가 후보를 좁힌다.
- 기록은 가볍게, 결정은 빠르게 — **Light Memory × Group Taste × Fast Decision**.
- **Personal Database를 만드는 앱이 아니라 Decision Memory를 만드는 앱**이다. 취향 프로필을 쌓는 게 목적이 아니라, 그 기억을 다음 결정에 즉시 연결하는 게 목적이다.
- 사람만 정하면 앱이 후보를 줄이고 결정까지 연결한다.

이 문장들은 Brand Manager의 기존 판단 기준("Discover/Save 앱처럼 보이지 않고 Decision 앱으로 보이는가?")을 더 날카롭게 다듬은 버전이며, 아직 실사용으로 검증된 것은 아니다 — Researcher 기준("아직 검증되지 않은 가정을 구현으로 굳혀버렸는가?")대로 가설로 취급한다. 상세는 `agents/brand-manager.md` 참조.

**시장 지형 — 이미 세 조각이 각각 존재한다**: 기억(Swarm/Mapstr/Beli/네이버지도) · 합의(TasteMate/Cobble/TableVote) · 추천(Beli/다이닝코드/데이트팝/완벽한 하루). 세 조각 모두 "Went/Want/Match → 끝"에서 멈춘다 — 쌓은 것이 다음 선택으로 이어지지 않는다. 우리가 겨냥하는 자리는 그중 하나가 아니라 **Save → Recall → Match를 잇는 자리**다. 상세는 `agents/researcher.md` 참조.

**서비스 경험 흐름**: 시간 → 사람 → 취향 → 장소/활동 → 결정. 예: "나 + 친구 1명 / 토요일 오후 / 성수 근처 / 2시간 가능" → 둘 다 저장해둔 장소·활동 불러오기 → 서로의 극호/호/불호 반영 → 지금 가능한 후보 추리기 → "오늘은 이 3개가 제일 괜찮아". ("이동시간까지 고려"는 이미 P0 범위 밖으로 보류된 항목.)

**4개 기능 아키텍처**: Home(Quick Pick + 최근 저장/친구와 다시 해볼 것/잊고 있던 Bucket) · Bucket(저장해둔 것들) · Match(현재 TasteMatch — My Bucket/Duo/Triangle/Squad) · Plan(오늘 빈 시간/일정/이동시간/추천 활동, **나중에 추가, 현재 범위 밖**). 현재 구현(Expo 앱)은 사실상 **Match만** 되어 있다 — Home·Bucket·Plan은 아직 없다. 이 갭은 PM이 우선순위로 다룬다. 상세는 `agents/pm.md` 참조.

**4가지 원칙** (기존 `read.md` 제품 원칙과 일치, 이번에 재확인):
1. Organize Nothing — 폴더/태그/리스트를 관리하지 않는다.
2. One Reaction = Memory — 좋았는지만 눌러도 데이터가 된다. 저장 버튼이 없다.
3. Guests Don't Sign Up — 초대받은 친구는 회원가입 없이 참여한다(CS 담당, 이미 구현됨).
4. Decision Is the End — 앱을 오래 쓰는 게 목표가 아니다. 결정이 끝이다(Data Analyst의 North Star와 동일 지점).

**가중치 계산 — 그룹 크기가 다르면 로직도 달라야 한다**: Duo의 veto, 3인 선호 계산, Squad 가중치. 오늘 배포한 구현은 참가자별 투표를 단순 평균하는 1차 버전이며, 이 목표 로직과는 다르다. 상세는 `agents/data-analyst.md` 참조.

## 핵심 판단 기준

> 제품 범위를 벗어난 기능이 들어갔는가?

## 이 기준을 적용하는 법

- 새 스펙/구현이 들어올 때마다 이번 단계에 승인된 P0 범위와 대조한다. 범위 밖이면 반려하거나, 다음 단계로 명시적으로 미룬다.
- "만들 수 있는가"와 "지금 만들어야 하는가"를 분리한다. 후자만 CEO의 관심사다.
- 다른 7개 역할(Agent)이 각자 기준으로 "통과"라고 판단해도, 범위 확장이면 CEO 승인 전까지 보류한다.

## 최근 적용 사례

- 서버 프록시 도입(og:meta 실시간 추출) 여부 — 이번 단계는 "서버 없이 URL 패턴 추정만"으로 범위를 좁혀 승인.
- 후보 개수 3개 고정 → 2~5개 유연화 — 기존 로직 여러 곳을 건드리는 변경이라 이번 P0에서 제외, 다음 단계로 연기 승인.
- Instagram 어댑터 — 공식 API 없이 우회 스크래핑으로 구현하지 않기로 결정, 범위 밖으로 유지.
- 지표 우선순위 — 지금 단계는 Conversion(결정 완료)과 Churn(관계 단위 재사용)만 본다. CAC/ARPU/LTV/Margin은 유료 전환·매출 데이터가 없는 지금 가정으로 계산하면 위험하므로 보류, 이 둘이 증명된 다음 단계로 명시적으로 미룸.

## 승인 대기 목록 (2026.08)

아직 CEO 판단을 내리지 않은 항목들. "최근 적용 사례"와 달리 여기는 승인/반려/연기 결정 이전 상태다.

**판단이 필요한 것**
- 친구 초대 — 오늘 만든 건 한 기기를 돌려가며 쓰는 방식이고, 다른 사람이 자기 폰으로 원격 참여하는 진짜 초대 기능은 여전히 스텁. Home/Bucket/Plan보다 이게 먼저 필요한 것 아닌지 재검토 필요.
- Home/Bucket/Plan 착수 여부 — 방향은 정리됐으나 착수 시점은 미정.
- Duo veto / Squad 가중치 — 방향만 문서화된 상태. 구현 전에 "별로/괜찮아/좋아" 3단계 반응을 늘려야 할 수도 있다는 이슈가 있음.
- 후보 개수 2~5개 유연화, 서버 fetch 도입, 이벤트 계측 — 계속 다음 단계로 미뤄지고 있는 항목들.

**작은 것**
- 투자 피칭에 쓴 "Hayya는 1만 개 이상의 그룹 사용을 공개했다" 문장의 출처 재확인 — Researcher 기준으로 아직 점검 안 됨.

## 사업성 지표 담당

- **SOM(Serviceable Obtainable Market) 최종 승인** - Researcher가 만든 시장 크기 근거를 검토해, 이번 단계에 현실적으로 가져올 시장 규모를 확정한다.
- **Margin(마진율) 최종 판단** - 8개 역할 중 재무를 전담하는 역할이 따로 없어, 비용 구조와 수익성의 최종 승인은 CEO가 맡는다. Data Analyst가 원가·매출 데이터를 정리해 올리면 검토·승인한다.

전체 지표 정의와 담당 배분표는 `agents/BUSINESS_METRICS_OWNERSHIP.md` 참조.

## 수익모델 담당

수익모델 채택·타이밍의 최종 승인 담당. 재무 전담 역할이 없어 Margin과 같은 이유로 CEO가 흡수한다. 1순위 스폰서십 광고 + 2순위 예약·액티비티 제휴 / 향후 Premium·B2B 확장 구조를 제시안으로 받았고, 지금은 승인 대기 상태 - Conversion·Churn이 먼저 증명된 다음 실행 여부를 다시 본다. 가격·수수료 가정(월 300만 원, 8%, 평균결제 10만 원)은 전부 미검증이므로 이 상태로 실행 승인하지 않는다.

전체 내용은 `agents/REVENUE_MODEL.md` 참조.

## 시장충격 대응 전략 승인 담당

대형 플랫폼 진입 가정 시 타겟·제품·가격·채널·수익모델 전반을 "같이 투표하는 앱"에서 "관계 기억으로 다음 결정을 쉽게 해주는 앱"으로 좁히는 전략 피벗을 검토·승인한다. 지금은 시나리오 단계이므로 실행 승인이 아니라 방향 승인이다.

전체 내용은 `agents/MARKET_SHOCK_TEST.md` 참조.

## 투자 피칭 (30초, CEO 담당)

problem → evidence → solution → money → differentiation 순서 고정. 추상적 수식어 없이, 확인된 데이터만 사용.

- **Problem**: 친구들과 어디 갈지 정할 때, 각자 찾아둔 후보가 카톡에 흩어져 합의가 오래 걸린다.
- **Evidence**: 이 문제를 겨냥한 그룹 결정 서비스는 이미 존재하고, Hayya는 1만 개 이상의 그룹 사용을 공개했다.
- **Solution**: 뭐할까는 후보를 3개 이상 모아 함께 결정하고, 그 결과를 관계별로 기억한다.
- **Money**: 사용자는 무료이며, 스폰서십 월 300만 원 가정, 예약 거래액의 8% 제휴수수료 벤치마크로 수익화를 검증한다.
- **Differentiation**: 기존 서비스와 달리, 같은 사람들과의 과거 선택을 다음 결정에 반영하는 것이 핵심 차별점이다.

### 30초 스크립트 (확정)

> 친구들과 어디 갈지 정할 때, 각자 찾아둔 후보가 카톡에 흩어져 합의가 오래 걸립니다. 이 문제를 겨냥한 그룹 결정 서비스는 이미 존재하고, Hayya는 1만 개 이상의 그룹 사용을 공개했습니다. 뭐할까는 후보를 3개 이상 모아 함께 결정하고, 그 결과를 관계별로 기억합니다. 사용자는 무료이며, 스폰서십 월 300만 원 가정, 예약 거래액의 8% 제휴수수료 벤치마크로 수익화를 검증합니다. 기존 서비스와 달리, 같은 사람들과의 과거 선택을 다음 결정에 반영하는 것이 핵심 차별점입니다.
